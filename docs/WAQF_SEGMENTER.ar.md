# الفاصل على الوقف (waqf segmenter): تقييم، غير مستخدَم حالياً

تقييم لنموذج تقسيم التلاوة على الوقف، اقترحه **محمد (Iam-Muslim)** صاحب
`QuranReciteToText`. مكتوب هنا للرجوع إليه لاحقاً؛ **لم نعتمده** في خط الإنتاج،
والأسباب مقيسة وموضّحة أدناه.

## النموذج

| | |
|---|---|
| الأصل | [`obadx/recitation-segmenter-v2`](https://huggingface.co/obadx/recitation-segmenter-v2)، 2.2 GB، يحتاج ~3 GB VRAM |
| المكمَّم | [`TheGreatQuran/recitation-segmenter-v2-quantized`](https://huggingface.co/TheGreatQuran/recitation-segmenter-v2-quantized)، `model_q8.onnx`، 561 MB |
| البنية | `Wav2Vec2BertForAudioFrameClassification` فوق `facebook/w2v-bert-2.0` |
| الدقة الزمنية | إطار كل 20 ms، تصنيف كلام/سكوت |
| المقاييس المعلنة | Accuracy 0.9958 · F1 0.9964 |
| الرخصة | MIT |

## ما الذي يحله أصلاً

تقطيعنا الحالي يعتمد على السكوت، وأحياناً تقع نقطة القطع **داخل الكلمة**
(نَفَس القارئ في وسط كلمة طويلة). فيُنسخ الجزآن منفصلين، ولأن نافذة المطابقة
ترجع 30 كلمة للخلف بعقوبة موضع ضئيلة، يطابق الجزء الثاني نفس الكلمة التي
استهلكها الأول، فتتكرر بموضع واحد وتوقيتين. رصدنا **7٬302 حالة** عبر الكوربوس.

القسمة على الوقف تمنع هذا من أصله بدل معالجته بعد وقوعه.

## لماذا لم نعتمده

**١. السرعة.** قِيس **1.6× الزمن الحقيقي** على M1.
خط الإنتاج الحالي كاملاً (ASR + مطابقة + محاذاة) يعمل عند **~17×**.
أي أن مرحلة التقسيم وحدها ستكون أبطأ عشر مرات من كل ما نفعله الآن.
لإعادة معالجة الكوربوس (194 ساعة صوت) ≈ **121 ساعة حوسبة** مقابل 3.62 ساعة للتشغيل الكامل الحالي.

**٢. لا يعمل على الخادم.** النسخة المكمَّمة `int8` **لا تُحمَّل أصلاً** على
VPS (x86_64، onnxruntime 1.23.2):

```
NOT_IMPLEMENTED : Could not find an implementation for ConvInteger(10)
```

تعمل بلا مشكلة على **arm64 (ماك، onnxruntime 1.29.0)**.
فالمسألة تغطية kernel في الـ runtime وليست عيباً في النموذج.
وهذه ثاني مرة يتعثّر فيها `int8` على هذا الخادم تحديداً؛ الأولى كانت
`qurankarim-fastconformer-q8` التي أخرجت كلاماً غير مفهوم هناك بينما عملت سليمة على arm64.

**٣. المكسب ليس في موضعه.** ما يهمنا هو حدود **الآية بالآية**، وهذا يتحقق
بالفعل: تغطية 95.5٪ و671٬339 كلمة موقّتة، والتكرار مُعالَج في `postprocess.py`.
النموذج يحسّن *طريقة* الوصول لا *النتيجة* المطلوبة.

## قياس فعلي (سورة الإخلاص، 20.3 ثانية)

```
audio 20.3s -> 1015 frames (20 ms/frame)
inference 12.6s = 1.6x realtime
speech=89.3%  silence=10.7%
segments: 5
   0.28 -  4.32  (بسملة)
   4.74 -  7.74  (آية 1)
   8.12 - 10.44  (آية 2)
  10.86 - 14.32  (آية 3)
  14.68 - 19.98  (آية 4)
```

تقسيم نظيف تماماً: بسملة + أربع آيات. الجودة ليست محل شك، المشكلة في التكلفة.

## كيف تشغّله لاحقاً

أصعب جزء هو تحضير السمات، لأن بطاقة النموذج تحيل على `transformers` بينما
`model_q8.onnx` يمكن تشغيله على `onnxruntime` وحده بلا PyTorch إطلاقاً.

التوقيع:

```
in : input_features  [batch, sequence_length, 160]  float32
out: logits          [1, frames, 2]                 float32
```

الـ160 = **80 mel × stride 2**، أي تُبنى 80 بُعداً ثم يُدمج كل إطارين:

```python
# SeamlessM4TFeatureExtractor مكافئ، بـ kaldi_native_fbank فقط
opts.mel_opts.num_bins   = 80
opts.frame_opts.samp_freq = 16000
opts.frame_opts.frame_shift_ms  = 10.0
opts.frame_opts.frame_length_ms = 25.0
opts.frame_opts.window_type = "povey"
opts.frame_opts.dither = 0.0

f = (f - f.mean(0)) / np.sqrt(f.var(0) + 1e-7)   # تطبيع لكل تلاوة
n = (len(f) // 2) * 2
f = f[:n].reshape(n // 2, 160)                    # stride 2
```

سكربت التجربة الكامل محفوظ في نفس جلسة العمل باسم `test_segmenter.py`.

## متى يستحق العودة إليه

- عند توفر **GPU** (النسخة الكاملة تحتاج ~3 GB VRAM وستقلب معادلة السرعة)
- أو عند ترقية `onnxruntime` على الخادم بحيث يدعم `ConvInteger` على x86_64
- أو إن احتجنا يوماً حدوداً **دون مستوى الآية** (كلمة/وقف داخل الآية)، فحينها
  يصبح التقسيم على الوقف هو الطريق الصحيح لا تحسيناً كمالياً
